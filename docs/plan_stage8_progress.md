# Стадія 8 — «Куди я йду»

Мета: гравець у будь-яку секунду знає, **над чим він зараз працює** і **скільки
лишилось**. Плюс прибираємо дві речі, які цьому заважають: розкидана по трьох
локаціях карта і покращення робітників, яке трапляється саме собою.

## Діагноз

Гра вже вміє підказувати — але тільки на один крок уперед. `hud.js/hint()`
каже «неси коробку до верстака», стрілка (`nextObjective` у `sim/derive.js`)
веде до найближчої корисної зони, а `PRIORITY` там — це список **дій циклу**:
mailbox → bench_out → bench → delivery_slot → trashbin → piggy → desk.

Тобто вся навігація гравця — це один оберт петлі «замов-запаяй-продай». Про те,
що паяльник 3-го рівня коштує $X і що до нього лишилось $Y, не каже **ніщо** —
це видно лише якщо самому дійти до шафи й відкрити модалку. А саме це і є
прогрес: петля не змінюється, змінюються апгрейди. Звідси відчуття «граю, а
нічого не відбувається».

Дві дрібніші речі з того ж кореня:

- **Три локації на дві потрібні.** Квартира і гараж — це один і той самий цех у
  двох кольорах: ті самі об'єкти, той самий цикл, різні цифри. А переїзд ще й
  **скидає гроші** (`startMoneyAt`), тобто накопичене до переїзду зникає — рівно
  та валюта, якою вимірюється прогрес.
- **Підвищення робітника витрачає гроші без питання.** Зона `promote` (F5)
  їде за працівником і спрацьовує через 1 с стояння поруч (`ZONE_DWELL_PROMOTE_MS`).
  Усі інші панелі — стіл, шафа, дошка — на dwell **відкривають модалку**; ця одна
  одразу списує $. Тому випадковий прохід повз техніка = мінус гроші і нуль
  пояснень.

## П1 — Квест-трекер

**Рішення: квести — це derived, а не збережений стан.** Той самий підхід, що й
`piggyShouldShow`/`upgradeNeedsAttention`: список активних цілей рахується зі
стану щокадру. Збережене — рівно одне поле: який квест гравець **закріпив**
тапом. Інакше довелось би тримати в сейві дерево квестів і мігрувати його при
кожній зміні балансу.

Новий модуль `src/sim/quests.js`:

```js
// { id, title, hint, cost(game), zoneKind, done(game), rank }
export function activeQuests(game)   // впорядковані, done відфільтровані
export function pinnedQuest(game)    // закріплений або перший активний
```

Кожен квест знає **три** речі: як називається, скільки коштує (для прогрес-бару
$є/$треба) і **до якої зони вести**. Останнє — саме `zoneKind` ('rack', 'desk',
'jobboard'), а не координати: зони вже існують у кожному layout, і квест не має
знати, де в цій локації стоїть шафа.

Стартовий набір (усе виводиться з наявних даних, нових балансних чисел нема):

| Квест | Джерело | Зона |
|-------|---------|------|
| «Замов перший дрон» | `idleStations` + жодної доставки | desk |
| «Покращ паяльник до N» | `UPGRADE_TRACKS.soldering` + `capFor` | rack |
| «Купи другий верстак» | трек `benches` | rack |
| «Найми першого техніка» | `hiringAllowed` + `nextHireCost` | jobboard |
| «Відкрий гараж» | вартість кімнати (П2) | rack |
| «Переїзд на фабрику» | `canMoveToLocation(state,'factory')` | rack |
| «Відкрий Цех 2/3» | `canUnlockHall` | rack |

Порядок (`rank`) — фіксований у визначенні квесту, не обчислюваний: «спочатку
паяльник, потім найм» — це дизайнерське рішення, а не формула.

**UI** — `src/ui/questTracker.js`, картка під грошима: заголовок, смужка
прогресу `$є / $треба`, тап по картці. Показуємо один квест (закріплений) +
згорнутий лічильник «ще N цілей»; розгортається тапом. На телефоні місця мало —
три картки з'їдять пів екрана.

**Тап → стрілка.** `nextObjective` отримує гілку: якщо квест закріплений і його
зона існує в layout — ведемо до неї, ігноруючи `PRIORITY`. Закріплення знімається
саме, коли квест виконано або гравець дійшов до зони. Мікро-підказка (`hud hint`)
лишається як є: вона про те, що **в руках зараз**, трекер — про те, **заради чого**.
Це дві різні речі, і зливати їх в одну не треба.

Нова подія `EV.QUEST_DONE` → звук `upgrade` + короткий тост. Без цього виконання
квесту непомітне, а весь сенс стадії — щоб прогрес було видно.

**Тести:** `quests.test.js` — для стану-фікстури активний квест той, що очікуємо;
виконаний зникає; закріплений веде стрілку до своєї зони.

## П2 — Гараж стає кімнатою квартири

Локацій лишається дві: **Квартира** (з гаражем як прибудовою) і **Фабрика**.

**Рішення: гараж — це кімната, яку купуєш, а не переїзд.** Механіка вже написана
двічі: `unlockHall` для цехів фабрики (F2) — це буквально «купив → layout
перебудувався → зросли ліміти персоналу». Гараж стає третім клієнтом того самого
коду, а не четвертим способом рости.

Що це дає крім однієї локації менше: **гроші більше не скидаються на середині
гри**. `startMoneyAt` спрацює тепер лише один раз — на переїзді на фабрику, де
скидання і задумувалось (нова глава з власним балансом).

### Дані

`apartment` у `state/locations.js` отримує `rooms` — так само, як фабрика має
`FACTORY_HALLS`:

```js
// defs/layouts/rooms.js
export const APARTMENT_ROOMS = [
  { id: 'flat',   cost: 0,   benches: 1, workerCaps: { … 0 },
    upgradeCaps: { soldering: 2, storage: 0, logistics: 0, consumables: 2, benches: 0 } },
  { id: 'garage', cost: 800, benches: 1, req: { soldering: 2 },
    workerCaps: { courier: 1, tech: 1, seller: 1, manager: 0 },
    upgradeCaps: { soldering: 3, storage: 1, logistics: 1, consumables: 2, benches: 1 } },
]
```

- `roleCapHere` вже вміє підсумовувати по відкритих одиницях — розширюємо його
  гілку `workerCaps: null` на квартиру.
- `capFor` стає максимумом по відкритих кімнатах (зараз — константа з локації).
- `hiringAllowed` — не поле, а «чи є хоч одна кімната з ненульовим `workerCaps`».
  Тобто найм з'являється рівно тоді, коли відкривається гараж, і дошка найму
  фізично стоїть у ньому.
- `LOCATION_ORDER` → `['apartment', 'factory']`; `unlockReq` фабрики додає
  `rooms: ['garage']` до наявних вимог по апгрейдах.

### Layout

`apartment` перестає бути константою і стає `buildApartmentLayout(state)` —
рівно як `buildFactoryLayout(unlockedHalls)`. Контракт той самий: повертає
об'єкт, який віддає `buildLayout`, і ніхто нижче не знає слова «кімната».

Гараж **зменшуємо** (як і просив): зараз це окремий світ 1500×1700; як прибудова
— приблизно **900×950**, приліплений праворуч до квартири. Світ стає ~1900×1350
замість двох світів 1000×1350 і 1500×1700. Двері між квартирою і гаражем —
звичайна `partition` з `gap`, тобто те, що `buildLayout` уже вміє; nav-сітка й
перешкоди підуть за нею самі.

Що всередині гаража: **2 слоти верстаків, дошка найму, пости працівників,
декор**. Стіл із ноутбуком, шафа апгрейдів, скарбничка, скринька і смітник
лишаються у квартирі — дублювати їх не можна, бо тоді гараж стає самодостатнім
і між кімнатами нема причини ходити. Вулиця і слоти доставки — спільні.

Поки гараж не куплено, на його місці — глуха стіна (не «затемнена кімната»:
показувати те, чого ще нема, це або спойлер, або баг на вигляд).

### Міграція сейвів

`main.js:97` уже мігрує `'workshop' → 'factory'`; поруч додається:
`locationId === 'garage'` → `locationId: 'apartment'`, `unlockedRooms: ['flat','garage']`,
**гроші лишаються як є** (не скидаємо — гравець за них уже заплатив переїздом).

**Тести:** `layout.test.js` — гараж досяжний із квартири по nav-сітці (у нас уже
є `reachability.test.js`, це його прямий випадок); ліміти персоналу до і після
покупки; міграція старого сейву.

## П3 — Підвищення тільки за згодою

Зона `promote` більше не витрачає гроші. Її `run` емітить
`PANEL_REQUESTED { panel: 'promote', workerId }` — далі як усі панелі (S2).

Нова маленька модалка `src/ui/promoteModal.js`: хто це, роль, рівень N → N+1,
**що саме зміниться** (з `roleLevelData`), ціна, кнопка. Списання переїжджає в
команду `promoteWorker` у `sim/commands.js` — там, де живуть усі інші покупки.

Дві деталі, без яких стане гірше, а не краще:

- `repeat: false` уже є, але модалка, що вискакує щоразу, коли ти проходиш повз
  свого техніка, дратуватиме сильніше за списання. Тому dwell росте з 1 с до
  **~1.6 с**: стояти поруч секунду можна випадково, півтори — вже ні.
- Над працівником, якого **можна** підвищити, з'являється значок `⬆ $120`
  (за зразком `burntLabel` у `sceneSync`). Зараз єдина ознака — підсвічена
  підлога під ним, і вона нічого не каже про ціну.

**Тести:** `promote.test.js` — стояння в зоні не змінює `money`; команда змінює.

## П4 — Продавець ближче до верстаків

Дрібниця з тієї ж скарги: продавець «гуляє» біля скриньки, тобто половину часу
його не видно біля роботи. Пости вже є в кожному layout (`spawns.posts`), і
`idleWander` уже водить робітника навколо свого поста — треба лише **пересунути
координати**: пост продавця стає на маршрут «вихід верстака → скринька», ближче
до верстаків, а не в кінці шляху.

Правити в трьох місцях: квартира, гараж-кімната (П2), `factory.js` (пости
рахуються від центру цеху). Чистий тюнінг координат, без коду.

## Порядок

1. **П2** (гараж-кімната) — найглибше в даних; квести мусять знати про кімнату,
   тож робити їх до неї = переписувати двічі.
2. **П1** (трекер) — головна цінність стадії.
3. **П3** (підтвердження) — незалежне, маленьке.
4. **П4** (пости) — тюнінг наприкінці, коли layout уже фінальний.

## Чого тут навмисно нема

- **Дерева квестів із гілками.** Прогрес у гри лінійний; дерево додало б стан у
  сейв і нуль сенсу.
- **Нагород за квести.** Нагорода за «покращ паяльник» — це паяльник. Окрема
  премія зверху зламала б увесь баланс цін, які й так налаштовані.
- **Третьої локації.** Фабрика лишається останньою і росте цехами (Стадія 5).
