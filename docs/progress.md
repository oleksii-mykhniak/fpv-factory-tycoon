# Прогрес реалізації

*Живий документ. Оновлюється після кожного під-етапу.*

## Робочий процес

*Оновлено 2026-07-25: більше не чекаємо на валідацію перед комітом.*
*Оновлено 2026-07-29: нотатки пишемо у файл стадії, а не в цей.*

1. Імплементуємо під-етап
2. Прогін перевірок: `npx vitest run`, `npm run build`, для рантайму — `npm run smoke`
3. `git commit` одразу + нотатка в `docs/progress/<стадія>.md` (**інсайти**, не список
   файлів: рішення, відхилення від плану, знайдені по ходу баги)
4. Йдемо далі; ти валідуєш на залізі коли зручно — фікси йдуть окремими комітами

Нова стадія: план у `docs/plans/`, факти — новий файл у `docs/progress/` і рядок у
таблиці нижче. Закрилась — план переїжджає в `docs/plans/done/`, а розділ «Що зараз»
називає наступну.

**Полагоджено 2026-09-11 (перша знахідка з валідації на залізі):** «+$47» над

(перевірка байтів бандла), а в налаштуваннях тепер видно коміт і дату збірки.

**Чекає валідації на залізі.** П'ять останніх стадій зроблені й закомічені, але
на пристрої не перевірені — це найдешевша річ, яку варто зробити наступною:

- **Стадія 14** (найбільше нового, тому й найперше): світ виріс до 5100×4600 —
  сім кімнат у трьох рядах; чи читається такий масштаб на телефоні й чи
  знаходить гравець прорізи між рядами. Головна сцена стадії — обліт: чи
  читається дрон у повітрі й чи не задовгі його 4.6 секунди вдесяте. Баланс
  чотирьох нових кімнат ($14k→$52k), очок дослідження й `FLIGHT_REJECT_QUALITY
  = 0.42` підбирався за столом.
- **Стадія 15**: чи не став верстак надто світлим поруч із рештою меблів; чи
  читається скарбничка; чи не втратили дрони різницю між типами на телефоні.
- **Стадія 13**: чи читаються значки ролей у натовпі з шести робітників; чи
  видно, ЯКИЙ дрон їде, за іконкою на плашці; чи не дрібні спрайтові цифри
  відліку на телефоні.
- **Стадія 12**: чи читається пара «прийом ↔ відвантаження» як пара; чи видно
  крапковий лічильник місткості ящика з масштабу камери; чи не загубилось
  прибуття без стрічки (звук + просідання ящика в сусідньому цеху).
- **Стадія 11**: чи не гринд норма збірок на Mk (`MK_BUILD_REQ = [3, 6, 10, 15,
  25]`); чи читається секція «Ваші люди» на дошці як те саме місце, де наймають;
  чи не забагато «продай N / збери N» підряд у 42 кроках ланцюга.
- **Стадія 10**: баланс нескінченних треків і Mk — числа підбирались за столом.

**Стадія 14 «Фабрика з кімнатами» ЗАКРИТА** ([план](plans/done/stage14_rooms.md),
[факти](progress/stage14_rooms.md)). К1–К5 виконані. Фабрика росте сімома
кімнатами п'яти типів: три цехи, лабораторія, відділ контрактів, майданчик
обльоту, склад. К6 (кімната сама розповідає, що з нею приїхало) і К7 (кімнат
скінченна кількість) виконані по ходу й закріплені тестами.

**Черга порожня — плану на наступну стадію немає.** Напрямок, записаний у К7:
коли кімнати закінчились, наступний крок — не восьма кімната, а **другий завод
(престиж)**: нова фабрика з бонусом від першої.

**Відкрите питання після Стадії 15:** три спрайти — `mailbox.png`, `lamp.png`,
`soldering_iron.png` — не малюються ніде. Видаляти чи лишити на майбутнє —
рішення власника гри, не рефакторингу.

Порядок був несучий і відпрацював: 12 принесла два нових об'єкти (приймальний
ящик і ящик відвантаження), 13 дала чим їх малювати — `npm run sprites`, — і 14
додала кімнати вже в чистий світ, а не малювала той самий арт двічі. Чотири нові
кімнати й три нові типи дрона намальовані генератором з першого разу.

## Загальні рішення і нові фічі

*Рішення, що стосуються кількох під-етапів або всього проєкту.*

- **2026-06-20** — у `KIT_TYPES` додано `assemblySteps[]` — масив назв кроків збірки для кожної точки пайки. Новий тип дрону = новий масив кроків. Ідея для майбутнього: після `finishAssembly` додати етап **тест-польоту** (анімована затримка 2–3с) перед тим як показувати фінальну якість і кнопку продажу — додає напругу і правдоподібність.
- **2026-06-20** — всі ігрові параметри, які можуть потребувати балансування, мають жити в `src/state/config.js` або у відповідному конфіг-об'єкті, а **не** як магічні числа прямо в коді. Це стосується: стартових грошей, вартості комплектів, параметрів міні-гри (швидкість, зелена зона), коефіцієнтів формули ціни, порогів поломки. Коли додаємо новий числовий параметр — одразу виносимо в конфіг. Поточний технічний борг: `money: 120` у `createState()`, `0.6`/`0.7` у `calcPrice`, `BASE_PERIOD_MS`/`SPEED_FACTOR` у `solderGame.js` — перенести до `config.js` під час наступного рефакторингу або перед 1.5.
- **2026-09-11** — перевіряємо **зібрану** гру, а не лише dev. Tree-shaking у
  `vite build` уміє вирізати робочий код (`docs/progress/fix_build_vs_dev.md`),
  і все, що бачив тільки `npm run dev`, про збірку не говорить нічого. Перед
  тим, як віддавати стадію на залізо: `npx vitest run` (включно з
  `src/scene/bundle.test.js`) → `npm run smoke:build`. Версію збірки видно в
  налаштуваннях — `0.2.0 · <коміт> · <дата>`; `+` після хеша означає, що
  зібрано з незакомічених змін.
- **2026-09-11** — анімація без тесту — це анімація, якої може не бути. Логіку
  кадру виносимо чистою функцією (як `floatPose` у `src/scene/floatGain.js`) і
  перевіряємо числами; на сцені лишається тільки застосування пози.
