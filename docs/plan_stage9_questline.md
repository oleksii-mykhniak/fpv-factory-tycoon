# Стадія 9 — «Один шлях» (ЗАКРИТА 2026-07-28)

Мета: у грі в кожен момент є **рівно одна річ, яку гра просить зробити**, і
кожна виконана річ **щось відкриває**. Ніяких паралельних систем підсказок,
ніякого магазину з усім одразу, ніяких апгрейдів, що ведуть назад.

## Діагноз

Стадія 8 додала квест-трекер, але не прибрала нічого — і тепер про «що робити»
говорять **три речі одночасно**:

1. `hud.js/hint()` — нижня панель, крок петлі («неси коробку до верстака»);
2. картка квесту вгорі + список «ще N» — по суті прайс-лист;
3. стрілка `nextObjective`, яку перебиває закріплений квест.

Три голоси на одну тему = шум. Плюс чотири окремі дизайнерські помилки, які
випливли на тесті:

- **Квести — це список покупок, а не сюжет.** Усі, крім `first_order`, мають
  вигляд «купи X за $Y». Гравець, який відкрив гараж і не знає, що робити,
  читає прайс-лист і не бачить **дій**. Немає жодного квесту виду «спаяй 4
  дрони», хоча саме дії — це те, чим гра грається.
- **Паяльник веде назад.** Трек: руками → руками ширше → **напівавтомат** →
  «паяльна станція», у якої `qualityMin` немає взагалі, тобто L3 **знімає
  автоматику** і повертає міні-гру. Це прямий регрес, і його видно.
- **Гараж нічого не дає — тому що нічого про це не сказано.** Насправді дає
  чимало (другий верстак-слот, `longrange_drone`, три вакансії, стелі
  soldering 3 / storage 1 / logistics 1 / benches 1). Але приходить це все
  одним тихим пакетом і без грошей на руках: гравець платить $800 і бачить
  порожню кімнату.
- **Шафа показує все одразу.** П'ять треків + кімнати + переїзд у момент, коли
  доступний рівно один, і викуплений трек лишається в списку назавжди.

## Принципи

- **П1. Один активний квест.** Одна картка. Немає списку, немає «ще N», немає
  закріплення (`pinnedQuestId` видаляється). Стрілка веде до нього.
- **П2. Квести — це ланцюг, а не множина.** Впорядкований масив кроків; крок N
  показується, коли N−1 виконано. Але зберігається так само нічого: кожен крок
  має `done(game)`, а всі умови **монотонні** (лічильники тільки ростуть,
  покупки не відкупаються). Активний квест = перший, у якого `done` false.
- **П3. Дія і покупка чергуються.** Кожен апгрейд заробляється циклом петлі, а
  кожен цикл веде до апгрейду. Ніколи дві покупки підряд без дії між ними.
- **П4. Один крок = одна знята рутина.** Апгрейд або прибирає ручну дію, або
  прибирає ризик, або відкриває нову — але не два за раз, інакше гравець не
  бачить, за що заплатив.
- **П5. Що не доступно — того не видно.** Панель поліпшень показує лише те, що
  тут можна купити зараз; викуплене до максимуму зникає.
- **П6. Кожен зворотний зв'язок живе там, де подія.** Згорів комплект → текст
  над **тим** верстаком і не зникає, поки не приберуть. Не тост, не модалка.

## Р1 — Ланцюг квестів замість списку ✅

`src/sim/quests.js` переписується: замість `QUESTS` (множина з `rank`) —
`QUEST_CHAIN` (впорядкований масив). Два типи кроку:

```js
// ДІЯ: прогрес — лічильник
{ id:'sell_three', kind:'do', zoneKind:'bench',
  title:'Продай 3 дрони', why:'Згорілий не рахується',
  have: g => g.stats.sold, need: 3 }

// ПОКУПКА: прогрес — гроші (як зараз)
{ id:'buy_iron', kind:'buy', zoneKind:'rack',
  resolve: g => ({ title:'Купи: Кращий паяльник', need: 150 }) }
```

API лишається того ж розміру:

```js
export function activeQuest(game)   // один крок або null (усе пройдено)
export function questIndex(game)    // індекс активного — потрібен Р5
```

**Лічильники (нове в стані).** Квести-дії неможливо вивести з поточного стану —
потрібна історія. Додається один об'єкт, усі поля монотонні:

```js
stats: {
  sold: 0,          // продано дронів (згорілий не існує — його не продати)
  assembled: 0,     // доведено до READY
  burnt: 0,         // згоріло комплектів
  bestQuality: 0,   // найкраща якість збірки
  soldByKit: {},    // { racing_drone: 2, ... } — для квестів на тип дрона
}
```

`SAVE_VERSION` → 4 **і `MIN_LOADABLE_VERSION` → 4**: старі сейви відкидаються,
усі починають заново. Спершу планувалось лишити підлогу на 3 (щоб не скидати
прогрес двічі підряд), але це неправильно по суті: уся послідовність гри тепер
виводиться зі стану, якого в сейві версії 3 немає. Технічно він читається —
`stats` заповнились би нулями, — тільки результат це шоп, який ніхто не
проходив: гравець із середини старої гри падає в середину ланцюга з нульовою
історією і половину відкриттів (картку кімнати, введення треків) не побачить
ніколи.

`outgrown(game)` — умова «ти вже далі» (маєш гараж / фабрику / робітників) —
лишається: акт, який `outgrown`, вважається пройденим цілком, і це страхує
будь-який стан, де гравець об'єктивно далі, ніж каже лічильник.

**Стрілка.** `nextObjective`: спершу — незавершена фізична дія (щось у руках,
готовий дрон на верстаку, згорілий верстак) за нинішнім `PRIORITY`, і лише
потім зона активного квесту. Це протилежно теперішньому (закріплений квест бив
усе) — і правильно: стрілка не має тягнути до шафи, поки в руках коробка.

**DoD:** на екрані ніколи більше однієї картки квесту; `pinnedQuestId` і
`.quest--sub`/`#quest-more` видалені з коду й CSS; тести на монотонність
ланцюга (кожен крок після виконання не повертається) і на `outgrown`.

один рядок + смужка; `hint()` живе в одному місці (questTracker), не в двох.

## Р3 — Паяльник тільки вперед ✅

| Рівень | Було | Стає |
|---|---|---|
| 0 Ручний | міні-гра | без змін |
| 1 Кращий | міні-гра, ширша зона | без змін |
| 2 Напівавтомат | сам 60–75%, поки хтось стоїть | без змін |
| 3 Паяльна станція | **міні-гра, автоматики немає** | сама **80–92%**, швидше за напівавтомат, перегріву нема |

Нові константи в `config.js`: `SOLDER_STATION_QUALITY_MIN/MAX = 0.80/0.92`,
`SOLDER_STATION_POINT_DELAY_MS = 900`, `SOLDER_STATION_MISS_CHANCE = 0.03`.

Чому це не вбиває найм техніка (саме через це L3 колись і зробили ручним):
**станція — це верстак, технік — це людина.** Станція все одно вимагає, щоб
біля неї **хтось** був (правило `workSource` не змінюється), а технік і є цей
хтось. Вони складаються: `workSource` уже бере найкраще по кожній осі, тож
станція **робить твоїх техніків кращими**. Це правильна форма для тайкуна:
апгрейд множить штат, а не конкурує з ним.

Свідоме наслідок: з L2 міні-гра з гри йде. Це і є «від ручного до автомату» —
рух, який гравець просив.

**DoD:** `levelData('soldering',3).qualityMin` визначено; тест «якість і
швидкість L3 не гірші за L2 по кожній осі» — щоб трек не міг зіпсуватись
балансом; текст ефекту оновлено.

## Р4 — Гараж як подія, а не як рахунок ✅

Гараж уже дає все потрібне. Треба зробити це **видимим** і **розтягнутим**:

1. **Картка «Кімнату відкрито»** одразу після покупки: що приїхало —
   `+1 верстак`, `+ Далекобійний дрон`, `+3 вакансії`, `паяльник до 3 рівня`.
   Дані беруться з `roomDef` (нове поле `unlocks: []`), тому те саме працює для
   цехів фабрики (`hallDef`) без другої реалізації.
2. **Наступний квест після гаража — «Найми кур'єра»**, зі стрілкою на дошку в
   гаражі. Порожня кімната перестає бути порожньою через один крок, а не через
   десять хвилин здогадок.
3. **Наймати можна не всіх** — це вже так: `courier/tech/seller` по одному,
   менеджер лишається фабричним. Це і є відповідь на «може дати наймати, але не
   всіх»: змінювати нічого, треба сказати гравцеві.

**DoD:** після `unlockRoom` показується картка з переліком; квест-ланцюг веде на
дошку найму; жодного нового балансного числа, крім текстів `unlocks`.

## Р5 — Прогресивне розкриття поліпшень ✅

`upgradeModal` фільтрує треки трьома правилами:

- `capFor(game, trackId) === 0` → трек тут не існує, **не показувати**;
- `level >= cap` → викуплено до стелі, **прибрати** (не «сірим», а зовсім;
  максимум по треку — не інформація, а сміття);
- трек, до якого ланцюг квестів ще не дійшов → **не показувати**. Кожен трек
  отримує `introducedBy: '<quest id>'`, а видимість — це
  `questIndex(game) >= indexOf(introducedBy)`. Нового стану не з'являється.

Кімната / цех / переїзд — та сама логіка: у списку лише те, що є наступним.

**DoD:** на старті в шафі видно один рядок (паяльник); після викупу треку рядок
зникає; тест «сума видимих рядків ніколи не 0, поки є що купувати».

## Р6 — Офлайн-дохід за закритий цех ✅

Зараз `settleOffline` лише доводить те, що вже було в роботі — бо ніхто не
замовляє комплекти без гравця. Це правильно, поки штату немає. Але коли
**менеджер + кур'єр + технік + продавець** усі найняті, петля замикається сама,
і саме це має бути нагородою за пройдений ланцюг: **цех працює вночі**.

Правило: якщо в поточній локації є хоч по одному з кожної з чотирьох ролей —
офлайн рахуються **повні цикли** аналітично:

```
цикл = max(доставка, точки × pointMs) / кількість верстаків
за цикл: −cost комплекту, +price(якість штату)
циклів = min(elapsedMs × OFFLINE_EFFICIENCY / цикл, скільки дозволяють гроші)
```

`OFFLINE_EFFICIENCY = 0.6` — грати наживо мусить бути вигідніше; ліміт
`OFFLINE_CAP_MS` (4 год) лишається. Звіт «Поки вас не було» отримує рядок
«Цех працював сам: N дронів, +$X».

**DoD:** без повного штату поведінка байт-в-байт як зараз (тест на це);
з повним — гроші ніколи не йдуть у мінус; чисті функції, тестується headless.

## Р7 — Згорілий комплект говорить, поки його не приберуть ✅

Мітка над верстаком уже є (`sceneSync` → `burntLabel`), але вона монохромна
13 px без фону і губиться, а решта зворотного зв'язку (звук + вібро) триває
пів секунди. Тому:

- мітка стає читабельною: підкладка, більший кегль, два рядки — **що сталось**
  («🔥 Перегрів на кроці «Паяю ESC»») і **що робити** («стань тут: утиль +$29»);
- висить, доки фаза `BURNT`, тобто поки хтось не прибере — уже так, лишається;
- те саме для холодної пайки: повідомлення `warning-cold` тримається
  `COLD_MSG_MS = 2500` замість одного кадру.

**DoD:** згорілий верстак читається без звуку і без модалки; текст не зникає
сам.

## Що змінилось проти плану під час реалізації

- **Ланцюг гаража довелось переставити.** Первісний порядок давав шість покупок
  підряд — тобто рівно той прайс-лист, проти якого вся стадія. Тепер між ними
  стоять дії («продай далекобійний», «продай 10», «збери 15», «якість 85%»), а
  тест `покупки не йдуть довгою чергою` тримає це правило в коді.
- **Р5 отримав третю умову видимості.** Двох із плану («стеля 0», «ланцюг не
  дійшов») було замало: шафа стояла порожня перші кроки. Додано «наступний трек
  ланцюга видно завжди».
- **Стрілка квесту вміє не показуватись.** Крок-покупка без грошей не веде до
  шафи — прогулянка до полиці, де нічого не купиш, це не підказка.
- **Смужка «0 / 1» прибрана** для одиничних дій: вона повторювала заголовок.
- **Фінальна ціль по $/сек** зберігає `stats.bestRate` (максимум), бо $/сек живе
  в журналі продажів, а не в стані гри, і поточне значення порушило б
  монотонність.
- **Офлайн не використовує `managerKitChoice`** — див. нотатку в `progress.md`.
- **Вставки живуть у `derive.js`, а не в ланцюгу.** Їхні умови не монотонні
  (згорілий комплект прибирають, гроші з'являються), тож у ланцюгу вони ламали б
  його головне правило. `interruptQuest(game)` перебиває картку, поки триває, і
  не рухає індекс. Формулювання плану «розбери його у смітнику» про згорілий
  комплект було неточне: комплект списують СТОЯЧИ БІЛЯ ВЕРСТАКА, а смітник —
  окреме джерело безкоштовних деталей, тому це дві різні вставки.
- **Тест Р5 знайшов справжній баг.** «Наступний трек ланцюга видно завжди»
  вказував на трек, навіть якщо той уже викуплений — і в квартирі з паяльником
  у стелі шафа ставала порожньою. `nextBuyTrack` тепер пропускає пройдені й
  безглузді кроки.

## Ризики

- **Ланцюг проти свободи.** Гравець може купити не те, що просить квест — і
  тоді крок просто вважається виконаним (умови ж монотонні), ланцюг сам
  проскакує вперед. Нічого не блокуємо: квест — це порада, а не двері.
- **Р5 може сховати потрібне.** Тому правило «не показувати те, до чого ланцюг
  не дійшов» діє лише в межах акту; коли ланцюг пройдено весь — видно все, що
  тут можна купити.
- **Р6 і баланс.** 0.6 та `OFFLINE_CAP_MS` — єдині ручки; обидві в `config.js`.
