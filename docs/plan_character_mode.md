# План: Стадія 3 — «Живий цех»

*Перехід від tap-driven маріонетки до керованого персонажа + автономних робітників у стилі
My Perfect Hotel / Idle Arcade — з переходом на симуляційну архітектуру (тік-луп + системи +
data-driven визначення станків, задач і ролей).*

Статус: **чернетка, не почато.** Попередній етап — `plan_demo_ready.md` (D1–D8 закриті).

## 0. Аудит поточної архітектури

Не «код поганий» — код чистий для того, чим гра є зараз (одна кімната, один воркер-маріонетка,
одна станція). Але рівно ці рішення блокують ціль. Конкретно:

### 0.1 Немає симуляційного лупу — є `draw()`, який мутує стан

`main.js:437-507` — `draw()` одночасно рендерить UI **і** приймає ігрові рішення: видає команди
воркеру (`commandDeliver`, `commandSolder`, `commandScrapPickup`), викликає `update(...)`, який
викликає `draw()` знову (`main.js:486` — `update(pickupDelivery(...)); return`). Тобто рендер
рекурсивно змінює стан. З двома агентами порядок цих викликів стає недетермінованим.

Прогрес часу живе в трьох різних місцях:
- `setTimeout` (`autoTimer`, `deliveryCheckTimer` — `main.js:93-94`),
- Excalibur `preupdate`-замикання в `scene.js` (`slotIndicators`, `piggy`, `barFill`),
- `actor.actions`-ланцюжки у `worker.js`.

Жодне з них не є єдиним джерелом «скільки минуло часу». Офлайн-прогрес, пауза, прискорення,
детерміновані тести — неможливі.

### 0.2 Стан продубльовано між `main.js` і `scene.js`

`scene.js:18-41` — вісім мутабельних модуль-глобалів (`currentPhase`, `_deliveries`,
`_activeSlotIndex`, `_piggyLastAt`, `_lastDroneSpriteKey`, …), які синхронізуються **вручну**
через `updateScene(refs, phase, piggyInfo, droneSpriteKey, deliveries, carryingSlotIndex,
scrapAvailable)` (`scene.js:663`) — сім позиційних аргументів, і кожна нова фіча додає восьмий.
Це найточніший симптом: сцена **читає копію** стану замість того, щоб бути його проєкцією.

### 0.3 Колбек-прошивка замість шини подій

`initScene(canvas, { onBoxPicked, onSolderRequested, onSellRequested, onLoadProgress,
onPiggyRequested, onSlotTapped, onTrashRequested, onScrapRequested, onScrapArrivedAtTrash,
onScrapDelivered })` — `scene.js:381`. Десять колбеків, по одному на взаємодію. Кожен новий
об'єкт у світі = новий колбек, протягнутий крізь три файли. Двадцять станків = двадцять колбеків.

### 0.4 Поведінка воркера захардкоджена ланцюжками дій

`worker.js` — окрема функція на кожну задачу (`commandDeliver`, `commandSell`, `commandTrash`,
`commandScrapPickup`, `resumeScrapSuccess`, `resumeScrapFail`), кожна з власним
`moveTo→callMethod→moveTo` ланцюжком, і кожна вимагає нових станів у таблиці переходів
`workerFSM.js:19-33`. Додати «віднеси брухт на склад» = правити 3 файли. Ланцюжок дій ще й
несумісний зі steering/A\* (їх не можна змішувати — `clearActions` посеред доставки вже давав
баг, див. `progress.md`, 2026-06-24).

### 0.5 Синглтон-стан

`state.phase` + `activeKit` + `solderPoints` + `assemblyQuality` — один верстак на гру.
`autoTimer` — один таймер збірки на гру. Два станки неможливі без рефактора.

### Що переїжджає без змін

`gameState.js` формули (`calcPrice`, `calcQuality`), `kits.js`, `upgrades.js` реєстр,
`locations.js`, `save/storage.js`, всі міні-ігри (`solderGame.js`, `trashModal.js`,
`piggyModal.js`) — вони чисті й нічого не знають про сцену. **Це і є цінне ядро, яке зберігаємо.**

## 1. Цільовий геймплей (один цикл)

```
Гравець бігає джойстиком/WASD по цеху
  ↓ зона 📦 СЛОТ ДОСТАВКИ (миттєво)     → бере коробку в руки (стек над головою)
  ↓ зона 🔧 ВЕРСТАК (утримання ~1.5 с)  → скидає коробку, станок стартує збірку
  ↓ [опційно] лишається в зоні верстака → міні-гра пайки = швидше й якісніше
  ↓ зона ✅ ВИДАЧА (миттєво)            → бере готовий дрон
  ↓ зона 📮 ПОШТА (утримання ~1 с)      → продаж, монети летять до HUD
```

Робітники роблять **той самий цикл**: ціль беруть із черги задач, шлях прокладає A\*, а зайшовши
в зону — виконують **той самий** обробник взаємодії, що й гравець.

> **Головний принцип:** одна реалізація взаємодії, два джерела наміру — ввід гравця та AI.
> Ніякого дубляжу правил.

Прогресія: гравець спершу робить усі 4 кроки сам → наймає кур'єра (крок 1) → техніка (крок 2–3)
→ продавця (крок 4) → далі лише замовляє кіти й розширює цех.

## 2. Цільова архітектура

### 2.1 Три шари, односторонній потік даних

```
       ввід гравця ─┐
                    ▼
┌───────────────────────────────────────────────────────┐
│  SIM  (чистий JS, нуль Excalibur, тікає фіксованим dt) │
│   world (серіалізовний) + systems[] + eventQueue       │
└───────────────────────────────────────────────────────┘
                    │ events + read-only world
                    ▼
┌───────────────────────────────────────────────────────┐
│  VIEW (Excalibur актори, DOM UI, звук, хаптика)        │
│   проєкція світу; НІКОЛИ не пише в world               │
└───────────────────────────────────────────────────────┘
```

`world` — звичайний серіалізовний об'єкт. Save = `JSON.stringify(world)`; VIEW не має власного
стану, який треба відновлювати. Це прибирає §0.2 цілком.

### 2.2 Тік-луп

```js
// sim/loop.js
const TICK_MS = 50                    // 20 Гц — досить для агентів, дешево на Android
export function advance(world, elapsedMs, systems) {
  let steps = Math.min(Math.floor(elapsedMs / TICK_MS), MAX_CATCHUP_STEPS)
  const events = []
  for (let i = 0; i < steps; i++)
    for (const sys of systems) sys(world, TICK_MS, events)   // фіксований порядок
  return events
}
```

Один виклик із `engine.on('preupdate')`. Наслідки:
- **детермінізм** — той самий вхід дає той самий вихід → сим тестується в Node без Excalibur;
- **офлайн-прогрес** — `advance(world, timeAway)` замість окремої формули-апроксимації;
- **пауза/прискорення** — безкоштовно (не викликаємо / викликаємо більше кроків);
- усі `setTimeout` зникають; таймери стають полями `world` (`readyAt`, `elapsedMs`).

### 2.3 Системи (це і є «стейт-лупи»)

Кожна система — чиста функція `(world, dt, events) => void`, що володіє **одним** зрізом стану.
Порядок фіксований і має значення:

| # | Система | Володіє | Що робить |
|---|---|---|---|
| 1 | `intentSystem` | `world.agents[].intent` | ввід гравця → вектор наміру; AI-агентам нічого не робить |
| 2 | `jobSystem` | `world.jobs` | `deriveJobs(world)` → reconcile; клейм/реліз задач |
| 3 | `agentSystem` | `world.agents[].task` | **луп робітника**: інтерпретує кроки поточної задачі |
| 4 | `pathSystem` | `world.agents[].path` | A\* на запит, інвалідація, кеш |
| 5 | `moveSystem` | `world.agents[].pos/vel` | слідування шляхом + steering + сепарація + колізії |
| 6 | `zoneSystem` | `world.zones[].occupants/dwell` | enter/stay/exit, накопичення dwell, `repeatMs`-тік |
| 7 | `interactionSystem` | — | застосовує zone-події через реєстр взаємодій |
| 8 | `stationSystem` | `world.stations[]` | **луп станка**: стадії, прогрес, вихідні предмети |
| 9 | `deliverySystem` | `world.deliveries` | таймери доставок, спавн коробок у слотах |
| 10 | `economySystem` | `world.money`, лог | продажі, витрати, статистика |

Додати нову механіку = додати систему в список або запис у реєстр. Ніяких змін у решті.

### 2.4 Шина подій замість колбеків

Системи не викликають UI — вони пишуть у `events`:

```js
events.push({ t: 'item.picked',      agentId, itemType })
events.push({ t: 'station.stageDone', stationId, stageId, quality })
events.push({ t: 'money.gained',      amount, atX, atY })
```

Після тіку VIEW робить один прохід по `events`: анімація, SFX, хаптика, спливаючі монети.
Замість десяти колбеків у `initScene` — один `subscribe(handler)`. Це прибирає §0.3.

### 2.5 VIEW як проєкція

`view/sceneSync.js`: `sync(world)` кожен кадр звіряє акторів зі світом —
створює актора для нової сутності, ставить `pos`/анімацію/z, видаляє зниклих. Жодних
модуль-глобалів, жодного `updateScene(a,b,c,d,e,f,g)`.

## 3. Data-driven визначення (ключ до розширюваності)

Конвенція проєкту вже така (`config.js` = числа балансу, `kits.js`/`upgrades.js`/`locations.js` =
контент). Продовжуємо її: **нова сутність у грі = новий запис у `defs/`, нуль нового коду.**

### 3.1 Станки — `defs/stations.js`

Станок описується стадіями; `stationSystem` — універсальний інтерпретатор цих стадій.

```js
workbench: {
  id: 'workbench',
  name: 'Верстак',
  inputs:  [{ item: 'kit_box',   capacity: 1 }],
  outputs: [{ item: 'drone',     capacity: 2 }],   // накопичувач: переповнився → станок стоїть
  // Стадії беруться з кіта (kit.assemblySteps) — станок лише виконує їх.
  stageSource: 'kit',
  work: {
    by:        ['worker:tech', 'player'],  // хто може обслуговувати
    autoRate:  0,                          // 0 = сам не працює; >0 = idle-станок (автопаяльник)
    playerBonus: { speed: 1.6, quality: +0.15 },  // присутність гравця
    minigame:  'solder',                   // яку міні-гру відкрити гравцю в зоні
  },
  zone: { dwellMs: 1500, w: 96, h: 64, offsetY: 40 },
  upgrades: ['soldering', 'consumables'],
}
```

Додати «3D-принтер рам», «тестовий стенд», «стіл упаковки» = ще один такий об'єкт. Нова
локація ставить їх у себе в layout — код не змінюється.

### 3.2 Задачі робітників — `defs/tasks.js`

Найважливіше для «різних задач для робітників». Поведінка = **скрипт із кроків**, не функція.

```js
haul_delivery: {
  id: 'haul_delivery',
  role: 'courier',
  priority: 10,
  // Коли задача взагалі має існувати (чиста функція від світу)
  when: (w) => w.deliveries.filter(d => d.arrived && !d.claimed),
  steps: [
    { op: 'goto',  target: 'job.from' },
    { op: 'take',  item: 'kit_box', count: 'carryCapacity' },
    { op: 'goto',  target: 'job.to' },
    { op: 'put',   item: 'kit_box' },
  ],
},
assemble: {
  id: 'assemble', role: 'tech', priority: 20,
  when: (w) => w.stations.filter(s => s.state === 'needsWork'),
  steps: [
    { op: 'goto', target: 'job.station' },
    { op: 'work', station: 'job.station', until: 'stageComplete' },  // луп, поки станок не звільнить
  ],
},
```

Ops інтерпретуються `agentSystem`: `goto | take | put | work | wait | emit | branch`.
Нова роль/задача («віднеси брухт на склад», «заправ витратники», «прибери робоче місце») =
ще один запис. Нуль коду, нуль нових FSM-станів. Це прибирає §0.4.

### 3.3 Ролі — `defs/roles.js`

```js
courier: {
  id: 'courier', name: 'Кур\'єр', emoji: '🏃',
  accepts: ['haul_delivery', 'haul_scrap'],
  hire:  { base: HIRE_COST_BASE.courier, growth: HIRE_COST_GROWTH },
  levels: [ { speed: 1.0, carry: 1 }, { speed: 1.25, carry: 2 }, { speed: 1.5, carry: 3 } ],
}
```

`state.workers: [{ id, role, level, hiredAt }]`. Наймати можна кількох однієї ролі — вартість
росте за `base × growth^n`.

### 3.4 Взаємодії — `defs/interactions.js`

Одна таблиця «тип зони × хто увійшов → що стається». Гравець і робітник ідуть сюди однаково.

```js
pickup_box: { dwellMs: 0,    accepts: 'any', run: (w, actor, zone) => takeItem(w, actor, 'kit_box', zone) },
bench_drop: { dwellMs: 1500, accepts: 'any', run: (w, actor, zone) => putItem(w, actor, zone.stationId) },
mailbox:    { dwellMs: 1000, accepts: 'any', run: (w, actor) => sellCarried(w, actor) },
```

### 3.5 План цеху — `defs/layouts/apartment.js`

```js
{ world: { w: 1600, h: 1200 },
  obstacles: [ {x,y,w,h}, … ],                    // → nav-сітка будується з цього
  stations:  [ { def: 'workbench', x: 800, y: 420 } ],
  spawns:    { player: {x,y}, restArea: {x,y}, deliverySlots: [{x,y},…] },
  theme:     { bgColor, floorColor } }             // те, що зараз у locations.sceneConfig
```

Переїзд у гараж = завантажити інший layout. Розширення цеху (купити 2-й верстак) = додати
запис у `world.stations` за координатами зі слоту в layout.

## 5. Фази

### C0 — Симуляційне ядро (без зміни геймплею)

Мета: перевести **поточну** гру на нову архітектуру, нічого не додаючи. Якщо гра після C0
виглядає й грається так само — рефактор вдався.

- **C0.1** `sim/world.js` — `createWorld()`, серіалізація, `migrateFromLegacy(save)`.
- **C0.2** `sim/loop.js` + `sim/events.js`; підключити до `engine.on('preupdate')`.
- **C0.3** Перенести таймери: `deliverySystem` (замість `deliveryCheckTimer`),
  `stationSystem` (замість `autoTimer`). Прибрати всі `setTimeout` з `main.js`.
- **C0.4** `view/sceneSync.js` — сцена стає проєкцією; прибрати модуль-глобали
  зі `scene.js` і `updateScene(...)` із 7 аргументами.
- **C0.5** `view/effects.js` — підписка на події; прибрати 10 колбеків з `initScene`.
- **C0.6** `main.js` худне до композиції: створити world → систем → view → підключити UI.
  `draw()` зникає як функція, що приймає рішення.

**DoD:** повний цикл (замовити → доставка → пайка → продаж → скарбничка → брухт) працює як
раніше; жодного `setTimeout` у грі; save/load сумісний зі старим; тести зелені.
**Ризик:** найбільша окрема зміна плану. Робити в гілці, не змішувати з C1.

---

### C1 — Світ, камера, ввід

- **C1.1** Світ більший за екран: координати в пікселях світу, не в частках екрана
  (`W * 0.38` → `layout`). Камера: `elasticToActor(player, …)` + кламп по межах світу.
- **C1.2** `inputVector.js` (чистий): deadzone `INPUT_DEADZONE`, нормалізація діагоналі,
  злиття джойстик+клавіатура.
- **C1.3** `joystick.js`: DOM-оверлей у `#ui-root`, **не** canvas — не конкурує з Excalibur
  pointer-подіями (цей конфлікт уже кусав у D4). Плаваюча база під пальцем у нижніх
  `JOYSTICK_ZONE_H_RATIO` екрана; `pointercancel` обов'язково; `touch-action: none`.
- **C1.4** `keyboard.js`: WASD + стрілки; ігнорує ввід, коли відкрита модалка.
- **C1.5** Гравець як сутність world (`kind: 'player'`), `intentSystem` пише його намір,
  `moveSystem` рухає — тим самим кодом, що й робітників.
- **C1.6** Колізії зі стінами/меблями: Excalibur `CollisionType.Fixed` для перешкод,
  або власний AABB-resolve у `moveSystem` (див. §6.1).
- **C1.7** Прибрати `worker.walkTo()` і free-walk pointer-handler.

**DoD:** бігаю персонажем джойстиком на телефоні і WASD на ноуті, камера стежить, крізь стіни
не проходжу.

---

### C2 — Тригер-зони + носіння предметів

- **C2.1** `systems/zone.js` + `defs/interactions.js`. Модель зони: AABB, `dwellMs`,
  `repeatMs` (0 = раз за вхід; >0 = потік предметів кожні N мс), `accepts`, `enabled(world)`.
- **C2.2** Dwell-індикатор: кільце над персонажем; вихід із зони → плавний спад
  (`DWELL_DECAY_MULT`), не миттєвий нуль.
- **C2.3** Носіння: `agent.carrying: [{item, meta}]`, ліміт `carryCapacity` (апгрейд).
  Візуальний стек над головою зі зміщенням і пружинним лагом.
- **C2.4** `repeatMs`-потік для розвантаження коробки й для монет — саме він дає
  «предмети перетікають до мене» фідбек із MPH.
- **C2.5** Перевести всі POI на зони; тапи прибрати.

**DoD:** повний цикл, жодного тапу по об'єкту в сцені. Видно, що персонаж несе; біля верстака —
кільце прогресу. **Це перша точка валідації напрямку** — далі йдуть дорогі фази.

### C6 — Міні-ігри в новій парадигмі

Правило: **гравець у зоні → бонус; гравець пішов → станок працює далі, повільніше/гірше.**
Міні-гра перестає бути модалкою, що вибиває з потоку.

- **C6.1** Пайка: технік паяє з якістю за рівнем; гравець у зоні верстака → відкривається
  `solderGame.js`, дає `playerBonus` зі `defs/stations.js`. Вихід із зони — без штрафу.
- **C6.2** Скарбничка / тіндер лишаються модалками (короткі, самодостатні); на час модалки
  ввід руху вимикається.
- **C6.3** Трек `soldering` перестає керувати режимом (`MANUAL/SEMI/AUTO`) — режим тепер
  визначається наявністю техніка. Трек впливає на якість і швидкість.

**DoD:** підбігаю до верстака під час автозбірки — вмикається пайка руками, якість вища;
відбігаю — технік домальовує сам.

## 6. Ключові технічні рішення (фіксуємо зараз)

1. **Зони — ручний AABB у чистій системі, не Excalibur-колайдери.** Детерміновано, тестується
   в Node, не залежить від фізичного кроку і `collisionstart`-квірків 0.32.
2. **Колізії агент↔стіна — теж у `moveSystem`** (swept AABB по осях). Тоді SIM повністю
   незалежний від Excalibur, і headless-тести бачать той самий результат, що й гра.
   Excalibur-фізика не використовується взагалі.
3. **Джойстик — DOM, не canvas.** Не конкурує з Excalibur pointer-подіями, легко стилізується.
4. **Один код взаємодії для гравця й AI** (`defs/interactions.js`). Робітник у зоні = палець
   гравця. Інакше отримаємо два розбіжні набори правил.
5. **Задачі виводяться зі стану, не персистяться.**
6. **A\* без резервації клітинок + м'яка сепарація** — резервація дає дедлоки на 5–10 агентах.
7. **`actor.actions` прибираються повністю** — рух тільки через `vel` у `moveSystem`.
   Змішувати action-ланцюжки зі steering не можна (уже кусало в D6).
8. **Фіксований тік 20 Гц, рендер — на кожен кадр.** Інтерполяція позицій у VIEW, щоб рух був
   плавним при 60 fps.
9. **Порядок фаз: C0 → C1 → C2 → пауза на валідацію → C3–C5.** Спокуса почати з A\* є, але
   без ядра й зон його нема на чому перевіряти.

## 7. Нові константи (`config.js`)

За правилом проєкту — жодних магічних чисел у коді.

```
// Симуляція
TICK_MS, MAX_CATCHUP_STEPS, OFFLINE_CAP_MS, PATHS_PER_TICK
// Рух
PLAYER_SPEED, WORKER_SPEED_BY_LEVEL[], INPUT_DEADZONE, ACCEL_MS
// Джойстик
JOYSTICK_RADIUS, JOYSTICK_DEADZONE, JOYSTICK_ZONE_H_RATIO
// Зони

// Носіння

// Навігація
```

Розподіл: `config.js` = числа, які крутимо для балансу; `defs/` = структура й контент

## 8. Тестова стратегія

Продовження наявної практики (157 тестів зелені). Головний виграш архітектури — **сим
тестується цілком, headless**:

| Модуль | Що тестуємо |
|---|---|
| `sim/loop` | детермінізм, catch-up кап, стабільність при великому `elapsedMs` |
| `systems/station` | стадії, накопичувачі, переповнення виходу, гравець-бонус |
| `systems/zone` | enter/stay/exit, накопичення й спад dwell, `repeatMs`, `enabled` |
| `systems/job` | derive зі стану, клейм/реліз, ідемпотентність reconcile |
| `systems/agent` | повний цикл кроків, обрив задачі, недосяжна ціль |
| `systems/move` | колізії AABB, сепарація, stuck-детект |
| `navGrid`/`astar` | растеризація, роздування, обхід, недосяжність→null, ліміт, детермінізм |
| `inputVector` | deadzone, діагональ, злиття джерел |
| `gameState` | наявне + station-API + дві паралельні станції |
| **інтеграційний** | «10 хвилин симуляції з 3 робітниками» → очікуваний дохід і нуль стуків |

Останній тест — найцінніший: він ловить дедлоки й економічні поломки без запуску гри.
